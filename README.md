# MiraiTech Markup Service

Внутренний инструмент MiraiTech для синхронного просмотра видео и IMU-данных сессии, разметки фаз контакта стопы и подготовки обучающих датасетов.

## Описание

Сервис используется командой разработки и аналитики для работы с сырыми данными сенсоров вне основного пользовательского приложения. Загружается видео записи теста и данные сессии — по ID через GCS-first канал companion API или из локального `.parquet`-файла. Доступ к сессии не зависит от её владельца: любой авторизованный пользователь разметчика может открыть сессию по ID.

На интерактивном графике (Plotly) отображаются показания стелек `ESP32_Sensor_1` и `ESP32_Sensor_2`: акселерометр, гироскоп и другие числовые колонки. Воспроизведение видео синхронизировано с курсором на графике — можно визуально сопоставить движение спортсмена с сигналом сенсора.

Детекторы шагов размечают интервалы контакта левой и правой стопы с опорой, оператор правит результат на графике — удаляет лишние шаги и дорисовывает пропущенные. Результат экспортируется в CSV с колонкой `Target` (0/1) для обучения ML-моделей, используемых в backend-анализе (каденс, контакт, прыжки).

## Ключевые возможности

- Авторизация через backend API (JWT)
- Общий список сессий всех аккаунтов и загрузка по ID
- Чтение Parquet напрямую из GCS с fallback для legacy-сессий в БД
- Импорт локальных `.parquet` и видеофайлов (drag-and-drop)
- Мультитрассовые графики Plotly с выбором колонок и сенсоров
- Производный канал `Sensor_Total_Weighted` — взвешенная сумма давления стельки
  (нуль-фазовый фильтр Баттерворта 25 Гц → нормализация по калибровке сессии →
  веса `0.05·S1 + 0.15·S2 + 0.50·S3 + 0.30·S4`), одна кривая на стопу вместо
  четырёх; логика идентична ноутбуку анализа силовых платформ, поэтому разметка
  ведётся по той же кривой, на которой обучается модель
- Сворачиваемая панель калькуляторов: Speed/Distance Predict, Step Detector
  T-Test, TKEO Cadence и Step Cadence
- Детектор прыжков **Jump events** — отрыв и приземление по всему телу, а не по
  каждой ноге отдельно: модель обучена по силовым платформам, где полёт начинается,
  когда земли лишается **последняя** нога, и кончается касанием **первой**. Поэтому
  у прыжка один интервал, и на графике он рисуется одной полосой без сдвига S1/S2.
  Тип движения задаётся селектором «Движение» — это входной канал модели, от него
  зависят найденные события. Веса v7 (разметка «стелька врёт» + hop-маска): на
  вертикальном прыжке замороженных TEST-атлетов F1@±20 мс = 0.995 / 0.989,
  ошибка времени полёта 4.5 мс (≈0.4 см высоты); прыжки с пола на плиту
  находятся в 94 % случаев (v4 — 60 %); слабое место — SL hopping
- Регрессор силы **Total GRF · по платформам** — суммарная вертикальная сила
  обеих стоп в %BW (100 = спокойная стойка), отдельной панелью `GRF %BW` поверх
  графика, плюс линия стойки. Обучен по двум силовым платформам; целью служит
  **плита после low-pass 20 Гц** — это определение, а не упрощение: ударный
  транзиент приземления выше 20 Гц физически не переносится инсолью с шагом
  30 мс, и ни один признак удара (acc, jerk, TKEO, давление, время полёта) его не
  восстанавливает. Поэтому сравнивать кривую надо с колонкой
  `Plate_Fz_total_lp20_pctBW` из `export_markup_parquet.py`; против сырой плиты
  пик приземления ниже примерно на 4–10 % по определению. Вес спортсмена —
  **входной канал модели**, а не только множитель для ньютонов, поэтому без веса
  калькулятор не запускается.
  Задеплоен прогон на расширенном корпусе (68 сессий, +3 атлета single-leg/mixed в
  train). На атлетах, которых модель не видела (12 сессий, 135 прыжков): RMSE
  кривой в контакте 44 %BW, пик приземления против 20-Гц плиты MAE 38 %BW,
  bias +30, slope 1.00 (предыдущая per-foot модель: slope 0.58, bias −43 против
  сырой плиты — систематическое сжатие пиков); против сырой плиты bias −7,
  MAE 37, p90 73 (было 100). Базовый прогон без расширения
  (`model_total/`, RMSE 39, MAE 32, bias vs сырая −13) лежит рядом.
  Карточка модели показана в панели рядом с числами. Отрыв и
  приземление берутся у того же плитного детектора, что и в Jump events, так что
  полосы полёта у обоих совпадают. Здесь нет клока платформы, только часы
  устройства, и это стоит несколько %BW (см. `verify_deployed_grf.py`)
- Кнопка **«Плиты»** в панели графика (рядом с «Углы» / «Дрейф») — ground truth
  прыжков по силовым платформам, то есть та самая разметка v7, на которой
  обучается Jump events (`plate_flight_gt.py`, порт `jump_model_plate_v7.ipynb`;
  на всех 149 сессиях корпуса совпадает с тетрадкой до сэмпла). Активна только если в
  загруженном parquet есть сила плиты в ньютонах: `Plate_Fz_N` из
  `export_markup_parquet.py` или `1:Fz` / `2:Fz` из синхронизированного корпуса
  (`Synched/`, `sportsmen_sync/`, имена `Left Foot` / `Right Foot` понимаются).
  Алгоритм: нуль каждой плиты по её разгруженному кластеру → досинхронизация
  плит к IMU по огибающей удара (±300 мс) → обе плиты < 20 Н, сшивка блипов
  ≤ 10 мс, пол 60 мс → отбраковка «стелька на полу мимо плиты» (кроме случая,
  когда обе ноги в свободном падении от плитного отрыва до плитного приземления —
  тогда стелька врёт, а плиты главнее, и это прыжок) → прыжок, если
  в 60 мс после приземления есть удар ≥ 0.3·p99 TKEO **или** обе ноги в свободном
  падении (медиана min(|a|L,|a|R) ≥ 7 м/с²). Зелёные полосы — принятые полёты,
  серые — маска (ни удара, ни падения / стопа мимо плиты / **прыжок с пола на
  плиту или с плиты на пол** — плиты видят только один край такого прыжка, и
  700 мс от этого края маскируются, а не учатся как земля): модель на маске не
  учится и не оценивается. Клик по полосе показывает статус, удар, падение, долю
  нагрузки стельки и для hop — единственный точный плитный край. Кнопка
  «в разметку» переносит полёты в S1 и S2 как интервалы
  `Target=1` (билатеральная конвенция детектора), заменяя текущую разметку
- Синхронизация видео и IMU (курсор, таймлайн, сдвиг S1/S2)
- Автоматическое обнаружение и визуализация пропусков в загруженных данных
- Разметка фаз контакта левой / правой ноги
- Экспорт размеченного CSV

## Требования

- Node.js 18+
- npm
- Запущенный MiraiTech Backend (для загрузки сессий и авторизации)
- Соседний чекаут `../MiraiTech-backend` — `calculator_api.py` импортирует
  калькуляторы оттуда напрямую (путь переопределяется `MIRAITECH_BACKEND_ROOT`).
  Модели Jump events и Total GRF берутся из
  `app/services/calculators/models/` бэкенда (`new_jump_model_byAdil.pt`,
  `jump_grf_total.pt`); если их там нет, недоступны только эти калькуляторы,
  остальные работают
- Действующие Application Default Credentials для Cloud SQL и GCS у companion API

## Пример использования

```bash
# Установка зависимостей
npm install

# Один раз авторизовать локальный companion API в Google Cloud
gcloud auth application-default login

# Проверка: команда должна завершиться без ошибки
gcloud auth application-default print-access-token > /dev/null

# Dev-сервер автоматически запускает локальный API калькуляторов
npm run dev
```

На Windows PowerShell для проверки используйте:

```powershell
gcloud auth application-default print-access-token *> $null
if ($LASTEXITCODE -eq 0) { "Google Cloud: OK" }
```

Если интерфейс уже открыт и показывает ошибку доступа, после `gcloud auth application-default login` остановите dev-сервер (`Ctrl+C`) и снова выполните `npm run dev`.

Приложение: http://localhost:5173

```bash
# Сборка
npm run build
npm run preview
```

**Типовой сценарий:**

1. Войти с учётными данными backend.
2. Загрузить видео теста и сессию (по ID или `.parquet`).
3. Настроить колонки, сдвиги S1/S2, построить график.
4. Запустить нужный детектор шагов (ходьба / бег / спринт) — найденные шаги
   сразу становятся разметкой.
5. Поправить её: клик по лишнему шагу на графике → «Удалить из Target» (или
   `Del`); пропущенный шаг добавить в режиме разметки, отметив его начало и конец.
6. Экспортировать CSV с колонкой `Target`.

Колонка `Target` — это шаги включённых детекторов за вычетом удалённых
оператором плюс интервалы, размеченные вручную. Удалённый шаг остаётся на
графике серым «призраком», его можно вернуть кликом или кнопкой «Вернуть
удалённые».

## Конфигурация

| Переменная | Описание |
|------------|----------|
| `VITE_API_BASE` | Базовый URL backend (пустая строка — использовать прокси Vite) |
| `VITE_API_PROXY` | Target для прокси `/api` в `vite.config.js` (по умолчанию backend) |
| `VITE_CALCULATOR_API` | URL companion API разметчика (по умолчанию `/calculator-api`) |
